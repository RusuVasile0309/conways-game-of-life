## What Went Well

**100% story completion with a full persistence stack delivered.** All four stretch stories landed. The save/load round-trip works end-to-end, and patterns now survive server restarts after Story 7.4. That's a meaningful, real user feature.

**Injection token abstraction paid off immediately.** The `PATTERN_REPOSITORY` string token was introduced in 7.1's code review as a design improvement. Three stories later, it enabled the entire in-memory → SQLite swap in 7.4 with zero changes to `PatternsController`. Good interface design at a decision point pays dividends down the sprint.

**Story 7.2 was the cleanest execution of the epic.** Exact function signatures, the `nodenext` + `.js` extension warning, `pnpm nx sync` behaviour — all pre-documented. First run was clean. Zero debug cycles. This reinforces the correlation between story file depth and first-run quality.

**Zod validation layer creates a typed safety net.** `savedPatternSchema.parse()` in `libs/api-client` means a malformed API response throws a typed error rather than producing silent bad data. This is the right kind of defensive design.

**Code review caught both HIGH CI issues before merge.** Story 7.1's typecheck gap (spec files in `tsconfig.app.json` without jest types) and Story 7.4's `prisma generate` gap (fresh clone would fail) — both found in review, not in CI. The review process is working.

**`useExisting` vs `useClass` insight documented.** The `useExisting` provider in `PatternsModule` prevents double-instantiation of `SqlitePatternRepository` and avoids doubled DB connections. This is a non-obvious NestJS DI detail, and capturing it in the story dev notes means future devs won't repeat the mistake.

## Challenges

**CI fresh-clone failures caught late (twice).** Story 7.1 had a typecheck failure on fresh clone (spec files in `tsconfig.app.json`, jest types missing). Story 7.4 had `@prisma/client` generate not running after `pnpm install --frozen-lockfile`. Both worked locally, both failed on CI. Root cause: the CI contract — "what does the environment need beyond `pnpm install`?" — was never written down. Each story discovered a new undocumented prerequisite.

**Story 7.3 had 5+ post-review fix commits.** CORS whitelisting only `localhost:3000` (web runs on `4200`), WCAG AA contrast failures on neutral-300 background (`neutral-400`, `neutral-500`, `red-600`, `amber-600` all fail 4.5:1), wrong `NEXT_PUBLIC_API_BASE_URL` env var name. These are all *knowable constraints* — they shouldn't be post-implementation discoveries. CORS origins and WCAG contrast ratios should be verified before committing.

**The `.js` extension rule is still causing friction in year three.** Explicitly flagged in Epic 5's retrospective. Appeared in 7.2 and 7.4 dev notes again. The rule is known and documented, but it lives in per-story notes rather than project-level constraints. It needs to be in CLAUDE.md.

**Architecture doc path mismatch.** `docs/planning-artifacts/architecture.md` specifies `apps/api`. Nx scaffolded to `api/`. Every story that referenced the API had to discover and note the actual path. The architecture doc has drifted from the scaffolded reality.

**Generator cleanup is not automatic.** Story 7.1 left `AppController` and `AppService` as dead code after they were removed from the module. Generators produce boilerplate that must be actively cleaned up — this is easy to miss.

---

## Key Insights

1. **Local ≠ CI: document every setup step `pnpm install` doesn't cover.** Two HIGH issues were CI-only failures. The fix is explicit dev notes (or CLAUDE.md), not better developers.

2. **Pre-verified story notes produce first-run implementations.** Story 7.2 proved it again — exact signatures, explicit constraints documented ahead of time → clean first run. This discipline is worth the upfront investment.

3. **Abstractions for known swap points are worth the extra 10 minutes.** The injection token was an optional improvement; its payoff in 7.4 was concrete and immediate.

4. **UI specs need WCAG contrast and CORS requirements as explicit ACs, not implementation details.** Both are knowable before the first commit. Discovering them post-implementation creates churn.
