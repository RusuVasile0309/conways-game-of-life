## What Went Well

**Structured BMAD story files dramatically improved AI adherence.** Epic 4 was the first epic to use the full create-story → dev-story → code-review workflow. The quality gap was visible and significant. AI working from explicit ACs produced more focused, on-spec implementations than AI working from epic descriptions alone.

**Code review caught real bugs (story 4.3):**
- CSS `@media (max-height: 667px)` without width constraint would override the desktop `height: 70vh` on short-height desktop viewports (e.g. DevTools open at 1280×640). Caught in code review; fixed by adding `and (max-width: 1023px)`.
- `isMobile: true` in `test.use()` was a no-op on Chromium — removed cleanly.
Both would have shipped undetected without the code review step.

**Playwright edge cases handled correctly:**
- `devices['iPhone SE']` cannot be spread inside `test.describe` `test.use()` — `defaultBrowserType: 'webkit'` forces a new worker. Resolved by using explicit `{ viewport: { width: 375, height: 667 }, hasTouch: true }`.
- `page.evaluate(string)` form used instead of arrow function to avoid TypeScript `dom` lib errors in the e2e tsconfig.
- Touch parity test strategy: tap canvas → click Play → assert gen-count advances from 0. Indirect but sound behavioral assertion.

**a11y audit surfaced and fixed real WCAG violations (story 4.2):**
- `text-cyan-600` on grey background failed axe color-contrast — fixed to `text-cyan-800`
- `text-cyan-600` on white background — fixed to `text-cyan-700`
- `text-neutral-500` on labels — fixed to `text-neutral-600`
All three were real violations that would have failed a WCAG 2.1 AA audit.

**WebKit scoped out cleanly (story 4.2).** Playwright's WebKit on macOS only tabs through form inputs by default (system "Full Keyboard Access" required for buttons). Rather than fighting the platform, CI was already Chromium-only and the architecture doesn't require multi-browser. Scoped out cleanly.

## Challenges

**Story 4.1: Dangling commit required clean re-implementation.** The happy-path spec existed as a dangling commit (`8310e1b`) that was never pushed or merged. Story 4.1 re-implemented it cleanly on a fresh branch. Minor process gap — a commit that doesn't make it into a PR is effectively lost work.

**Story 4.2: Tab reachability fix crossed epic boundaries.** The root cause was the empty-grid `disabled` guard introduced in story 3.4 (Epic 3). The fix — removing `disabled` from Play and simplifying Step to `disabled={isRunning}` — was the right call, but the a11y regression was avoidable had the guard been reviewed for tab-reachability when it was first introduced.

**AI adherence to docs at 50–60% without story files (epics 1–3).** The structured workflow in Epic 4 demonstrated what was missing earlier. The BMAD procedures add upfront overhead but reduce correction cycles during implementation.

**AI thinking loops on Playwright errors.** When Playwright tests failed, AI would enter extended diagnostic loops rather than isolating the specific failing assertion. Re-directing to read the raw error output (not the symptom chain) resolved these faster.

---

## Key Insights

1. **The create-story → dev-story → code-review loop is the highest-leverage process improvement in this build.** Epic 4's story files gave AI a testable contract. Code review caught real bugs. The process overhead was justified by the quality output.

2. **Code review is not optional for AI-generated code touching CSS media queries or Playwright config.** Both bugs caught in story 4.3 review were subtle, framework-specific issues that AI generated confidently but incorrectly. Human review of these areas is not overhead — it's the quality gate.

3. **Playwright and CSS have framework-specific constraints that require FE expertise to catch.** `devices['iPhone SE']` Playwright quirk, CSS media query cascade, `page.evaluate` string form for TS — these require knowledge that AI doesn't reliably apply. This is where the 20% human correction contribution lives.

4. **Dangling commits are a process gap.** Work that doesn't make it into a PR is invisible to the team and can create confusion. Commit → push → PR should be the atomic unit of work.
