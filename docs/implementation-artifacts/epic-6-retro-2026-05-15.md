## Challenges

Bob (Scrum Master): "Now the harder part. 6.2 has a failing E2E test. Let's understand it."

**Story 6.2: OffscreenCanvas + ResizeObserver interaction is non-trivial.**

After `canvas.transferControlToOffscreen()` is called, the main-thread canvas element enters a "transferred" state. In Chromium, setting `canvas.width` or `canvas.height` on a transferred canvas throws `InvalidStateError`. The `GameCanvas` `ResizeObserver` callback sets these dimensions — it fires almost immediately after mount, after the transfer has occurred.

Charlie (Senior Dev): "The current 6.2 implementation calls `transferControlToOffscreen()` in a mount-only `useEffect`, then the `ResizeObserver` fires and tries to set `canvas.width = container.clientWidth`. That throws."

Dana (QA Engineer): "Which explains the E2E failure. The gen-count stays at 0 because the ResizeObserver error disrupts the canvas dimensions being communicated to the worker. The worker's `cachedCanvasW` and `cachedCanvasH` stay 0."

Elena (Junior Dev): "The worker still posts back the `grid` message even when `cachedCanvasW` is 0 — but only because the tick handler doesn't check canvas dimensions before posting the grid. So why doesn't the generation counter advance?"

Charlie (Senior Dev): "Good question. Let me think through the flow: the ResizeObserver throws before `draw()` is called, meaning the worker never receives `{ type: 'draw' }` with valid dimensions. But the `tick` message does go through when `isRunning` becomes true... unless the worker itself errors on the `init` message because the ResizeObserver error happens before the worker processes `init`."

Bob (Scrum Master): "The root cause needs more investigation — likely an ordering issue between the `init` message, the `ResizeObserver` error, and the first `tick`. The fix is clear though: the `ResizeObserver` must communicate canvas dimensions to the worker via message rather than setting them directly on the transferred canvas."

**The fix pattern:** Replace `canvas.width = container.clientWidth` in ResizeObserver with a `{ type: 'resize', canvasW, canvasH }` message to the worker. The worker updates its cached dimensions and redraws. The main thread reads `canvas.width` for the `draw` call payload (reading is still valid after transfer in Chromium).

**JSDOM `transferControlToOffscreen` stub was needed in jest.setup.ts.** JSDOM does not implement this method — any Jest test that mounts `GameCanvas` would throw. The stub was added in 6.2 commit: `HTMLCanvasElement.prototype.transferControlToOffscreen = function() { return { getContext: () => null, width: this.width, height: this.height } }`. This pattern should be noted for future.

Bob (Scrum Master): "The second challenge is technical: we have a committed but unmerged story 6.2 on a feature branch with a failing E2E. The PR can't merge until that test passes."

## Key Insights

1. **OffscreenCanvas integration has a non-obvious lifecycle constraint.** After `transferControlToOffscreen()`, the main thread canvas is read-only for dimensions. Any code that writes `canvas.width` or `canvas.height` post-transfer throws. `ResizeObserver` callbacks need to be updated to message the worker instead. This should be a mandatory note in any future story that uses OffscreenCanvas.

2. **Performance profiling is most valuable when done at the boundary, not end-to-end.** The renderer bottleneck (batched draw) was only visible because the worker isolated `step()` computation. Profiling through layers reveals layer-specific costs that are invisible at the top-level flamechart.

3. **The `buffer.slice(0)` copy is cheap at current grid sizes but will become measurable at very large sizes.** 40KB at 200×200, negligible. At 500×500 (250KB per tick at 60 gen/sec = 15MB/s of allocations), GC pressure will become measurable. Double-buffering (the architecture §5.3 note about "future optimization") is the path forward.

4. **Epic execution order flexibility is real.** Epics 7 and 8 shipped before 6.2 because the blocker (NFR5) was already cleared by 6.1. The sprint-status model handles this correctly — stories are tracked independently of epic completion status.

5. **E2E tests are the right gate for async worker behaviour.** Jest + JSDOM mocks the Worker to a no-op, so unit tests cannot verify the actual simulation loop. The Playwright happy-path E2E is the only test that exercises the real browser, real Worker, and real RAF loop. When it fails, it means something fundamentally wrong with the integration — not a peripheral concern.
