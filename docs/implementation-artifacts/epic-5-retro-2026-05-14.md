## What Went Well

**Story 5-1 was a zero-debug-cycle implementation.** The story file had pattern coordinates pre-verified, the allocation strategy explained (`cloneGrid` once → mutate `Uint8Array` directly, avoiding 36 allocations for the Gosper gun), and the test approach spelled out. 35 tests, 6 suites, green in 0.25 seconds on first run.

**The `placePattern` design is clean and testable.** Pure function, immutable input, reference-distinct output. The contract is meaningful: glider translates (+1,+1) in 4 steps, blinker oscillates period-2, out-of-bounds cells clip silently. These are behavioral assertions, not coverage-padding.

**Native `<select>` was the right accessibility choice.** Keyboard support (Tab, Enter, Arrow), screen-reader compatibility, and focus management for free. No custom ARIA, no focus trap logic, no browser inconsistency fights.

**Auto-resize + centering delivered the right UX.** Users don't think about grid size before loading the Gosper gun — the grid expands to `pattern + 4` padding and centers the pattern automatically. The +4 border ensures the pattern isn't flush against the edge.

**GosperGliderGunIcon as a stylised representation was the right call.** A pixel-perfect 36×9 structure at 20×20 icon size would be unreadable. A three-row stylised suggestion of the gun structure communicates intent clearly.

**SVG-in-option browser limitation caught at design time.** The dev notes documented the constraint before implementation: browsers don't render SVG inside `<option>` elements. The last-selected icon displayed alongside the `<select>` was the designed-around solution.

## Challenges

**`.js` extension in `libs/sim` relative imports is a recurring gotcha.** `patterns.spec.ts` was written without `.js` extensions on relative imports — Jest passed locally, but `tsc` failed on CI typecheck. The rule was documented in the story-5-1 dev notes but still needed to be applied manually. node16 moduleResolution requires explicit `.js` for relative imports within `libs/sim`.

**Tab-order E2E test requires manual update whenever a new interactive control is added.** Adding `PatternSelector` inserted a new `<select>` into the Tab sequence between Randomize and Width, breaking the existing assertion sequence in `a11y.spec.ts`. This is the second time this pattern has occurred (first: story 4.2 Tab reachability fix). The test is doing its job — it caught the regression — but the update should be a mandatory subtask in any story that adds a focusable control.

**Mobile layout constraint not spec'd in AC.** The `PatternSelector` container had `w-full` which forced it onto its own line instead of sharing the Clear/Randomize row. Removing `w-full` fixed it, but this was a post-implementation discovery. Mobile row-sharing constraints should be explicit in story ACs.

## Key Insights

1. **Story file quality directly determines first-run implementation quality.** Story 5-1 had the tightest dev notes of any story so far — pre-verified coordinates, explicit algorithm choice, test approach spelled out — and it landed in zero debug cycles. The investment in story file depth pays off immediately.

2. **The Tab-order E2E test update is now a predictable task, not a surprise.** It has happened twice (stories 4.2 and 5.2). It should be a standard subtask in any story that adds or removes an interactive control, not something discovered at CI failure time.

3. **`nx affected -t typecheck` is the right gate for libs/sim changes.** Jest passes without `.js` extensions; tsc does not. Running typecheck explicitly is not optional when touching `libs/sim` — it catches what Jest misses.

4. **`libs/sim` is cleanly shaped for Epic 6.** The `Uint8Array`-backed `Grid` type is transferable across Worker boundaries at zero copy cost. `placePattern` stays in the main thread (one-shot, user-triggered), `step()` moves to the worker. The separation is natural.
