## What Went Well

**rAF accumulator implemented correctly (story 3.5).** The `useSimulationLoop` hook with `requestAnimationFrame` + time accumulator + `useRef` for `genPerSec` — allowing mid-run speed changes without restarting the loop — matched architecture §5.2 exactly. This was the most complex single technical deliverable in the MVP and it worked.

**Intentional sequencing of 3.3 → 3.5.** Story 3.3 used a temporary `setInterval` loop with the explicit intent of replacing it in 3.5. The sequencing worked cleanly — the interim implementation was never merged to main as the final state.

**`getBoundingClientRect()` hit-testing (story 3.2).** The pointer event → canvas coordinate conversion via `getBoundingClientRect()` was correct on the first pass and handles CSS scaling transparently. No coordinate bugs.

**Rabbit/turtle slider icons.** AI suggested the visual metaphor for the speed slider endpoints. Small UX detail that communicates the range without relying on numbers.

**Human UX decisions that improved the product:**
- Submit button removed from size form (story 3.1) — resize on `onChange` is more responsive
- Canvas sized to container via CSS zoom/pan approach — keeps pixel coordinates stable

---

## Challenges

**AI accuracy dropped significantly vs. Epic 2.** React state + `useRef` + `useEffect` + `requestAnimationFrame` is a more complex interaction surface. Multiple correction cycles were needed to get state management right — specifically: too much logic in `useEffect`, not enough in stable refs.

**AI entered long reasoning loops on runtime errors.** When errors appeared, AI would diagnose, propose a fix, hit a new error, and iterate — sometimes chasing the wrong variable for several steps. This required stopping AI and redirecting to the specific failing line rather than the general symptom.

**Story 3.4 introduced hidden accessibility debt.** The empty-grid `disabled` guard on Play and Step buttons was AI-suggested as a UX improvement. It was accepted without foreseeing that it would prevent Tab focus from reaching those buttons on page load — a WCAG violation surfaced in story 4.2. The guard logic was correct for UX purposes but had an unintended side effect that crossed story boundaries.

**No BMAD story files for Epic 3.** The biggest input in this epic was explaining to AI how the UI should look and work — grid rendering, button layout, the play/pause state machine. Without structured story files, this relied on verbal direction and back-and-forth, which consumed more time than the Epic 4 structured approach.

---

## Key Insights

1. **The complexity cliff between Epic 2 and Epic 3 is real.** Switching from pure functions to React lifecycle + rAF required significantly more human correction. AI accuracy dropped from ~95% (Epic 2) to ~75% (Epic 3 estimate).

2. **AI-suggested UX guards need accessibility review.** The empty-grid `disabled` guard was good UX but bad a11y. A brief accessibility lens ("can a keyboard user still tab to this?") at the time of suggestion would have caught it.

3. **Structured story files (or explicit product decisions up front) reduce the explanation overhead.** The biggest time cost in Epic 3 was explaining intent — how the UI should look, what state transitions to implement. An explicit story file with ACs would have substituted for some of that verbal direction.

4. **`setInterval` → rAF sequencing was the right call.** Implementing a temporary loop in 3.3 and replacing it in 3.5 kept each story focused. No rework, clean handoff.
